# AleCoin (ALE) — дизайн-спецификация

Дата: 2026-09-21
Статус: одобрено (устно), готово к планированию реализации

## Контекст и цель

Учебный проект #2 в серии "вайбкодинг" Антона (см. проект #1 — "0x Coffee",
`github.com/0xm1dn1ght/0x-coffee`). Цель — портфолио-проект, демонстрирующий
работу со смарт-контрактами и Web3-фронтендом, в отличие от лендинга проекта #1.

Тема: Антон и его друзья любят ирландский эль — токен назван в его честь.
Тикер **ALE**, имя **AleCoin**.

## Ключевая механика: ручная выдача наград

Когда друг покупает бутылку ирландского эля, Антон **лично решает**, кто
заслуживает награды в ALE. Это осознанное решение — выдача не автоматизирована.

Поток:

1. Антон открывает скрытую админ-страницу сайта (работает с iPhone), подключает
   MetaMask mobile.
2. Вводит адрес друга и сумму ALE.
3. MetaMask подписывает off-chain сообщение (адрес получателя + сумма +
   уникальный nonce) — приватный ключ Антона никогда не вводится вручную,
   подпись делает сам кошелёк.
4. Страница формирует ссылку вида
   `site.com/claim?to=...&amount=...&nonce=...&sig=...`. Антон отправляет её
   другу в Telegram.
5. Друг открывает ссылку на публичном сайте, подключает свой кошелёк, жмёт
   «получить».
6. Сайт вызывает `claimReward(address to, uint256 amount, uint256 nonce, bytes signature)`.
7. Контракт проверяет через `ecrecover`, что подпись принадлежит адресу
   Антона (`owner`), и что `nonce` ещё не использован. Если всё верно —
   переводит ALE на кошелёк друга и помечает `nonce` использованным.

Backend-сервер и база данных не нужны — вся проверка на стороне контракта,
сайт остаётся полностью статичным.

## Сеть

**Polygon.**

- Разработка и тестирование — тестовая сеть **Polygon Amoy** (бесплатно).
- Финальный деплой — **Polygon mainnet** (недорого, токен существует реально,
  в отличие от тестовой сети).

## Токен

Стандартный **ERC-20** с фиксированным `totalSupply`, весь объём минтится при
деплое на адрес Антона (`owner`) — часть предназначена для раздачи наград,
остальное может быть добавлено в пул ликвидности позже (см. «Опционально»).

## Архитектура

1. **Смарт-контракт `AleCoin.sol`** (Solidity, OpenZeppelin ERC-20 как база)
   - Стандартные ERC-20 функции (unchanged).
   - `claimReward(address to, uint256 amount, uint256 nonce, bytes signature)`:
     - Восстанавливает подписанта через `ecrecover` над хэшем
       `(to, amount, nonce, адрес контракта)`.
     - Требует, чтобы подписант == `owner`.
     - Требует, чтобы `nonce` не был использован ранее (`mapping(uint256 => bool) usedNonces`).
     - Помечает `nonce` использованным, переводит `amount` токенов на `to`.
     - Эмитит событие `RewardClaimed(address indexed to, uint256 amount, uint256 nonce)`.
   - Владелец (`owner`) задаётся при деплое как адрес Антона.

2. **Скрипты развёртывания** (Hardhat)
   - Скрипт деплоя, параметризуемый сетью (`--network amoy` / `--network polygon`).
   - Конфигурация сетей Amoy и Polygon mainnet через переменные окружения
     (RPC URL, приватный ключ деплоера — из `.env`, не коммитится).

3. **Публичный сайт** (React/Next.js, статическая сборка, GitHub Pages, без backend)
   - Главная страница: подключение кошелька, баланс ALE, перевод токенов
     другим адресам, история операций (через чтение событий контракта).
   - Страница `/claim`: разбирает `to/amount/nonce/sig` из query-параметров,
     подключение кошелька получателя, кнопка «получить» → вызов
     `claimReward`.
   - Блок «как получить код» со ссылкой на Telegram Антона (для тех, кто
     попал на сайт без ссылки-приглашения).

4. **Админ-страница** (скрытый, не проиндексированный маршрут на том же сайте)
   - Подключение кошелька Антона.
   - Форма «адрес получателя + сумма ALE».
   - Генерация nonce (например, `Date.now()` или случайное число — уникальность
     обеспечивается тем, что подпись+nonce одноразовые для данного получателя),
     запрос подписи через MetaMask (`eth_signTypedData` или `personal_sign`),
     сборка готовой ссылки для копирования/отправки в Telegram.

## Безопасность и обработка ошибок

- **Повторное использование ссылки-кода** → контракт отклоняет по уже
  потраченному `nonce` (`usedNonces[nonce] == true`).
- **Поддельная подпись** → восстановленный через `ecrecover` адрес не
  совпадает с `owner` → транзакция отклоняется.
- **Перехват ссылки третьим лицом** не представляет риска — ссылка жёстко
  привязана к адресу получателя (`to`), перехватчик не сможет перенаправить
  перевод на свой адрес, не имея подписи Антона на этот адрес.
- Приватный ключ Антона никогда не покидает MetaMask — ни на сайте, ни в
  скриптах деплоя (для деплоя используется отдельный ключ деплоера из `.env`,
  не связанный с `owner`-кошельком, либо тот же кошелёк, подключаемый вручную
  на момент деплоя — решается на этапе реализации).

## План тестирования

- **Юнит-тесты контракта** (Hardhat + Chai):
  - обычный перевод (стандартный ERC-20 `transfer`);
  - `claimReward` с валидной подписью и новым `nonce` → проходит, баланс
    получателя увеличивается, `nonce` помечается использованным;
  - повторный `claimReward` с тем же `nonce` → отклоняется;
  - `claimReward` с поддельной подписью (не от `owner`) → отклоняется.
- **Ручной прогон** полного сценария «Антон создаёт ссылку → отправляет в
  Telegram → друг открывает сайт и жмёт получить» в тестовой сети Amoy перед
  выходом в mainnet.

## Опционально: ликвидность на Uniswap

Добавить пул ликвидности на Uniswap (поддерживает Polygon) на символическую
сумму ($10–30), чтобы токен был реально покупаем за настоящие деньги.

Доступность интерфейса Uniswap и связанных RPC-сервисов из России **не
проверена** — проверяется по ходу реализации; при недоступности — решение
через собственный RPC-эндпоинт или VPN, по аналогии с миграцией проекта #1
с Cloudflare Pages на GitHub Pages.

## Хостинг и локализация

- Публичный сайт — статическая сборка на **GitHub Pages** (как у проекта #1;
  Cloudflare Pages исключён — недоступен без VPN в России).
- Стандартная локализация — под Россию (простой русский язык в интерфейсе),
  если не будет сказано иначе.

## Вне рамок этой спецификации

- Дизайн UI/UX сайта (цвета, шрифты, компоновка) — прорабатывается отдельно
  на этапе реализации фронтенда.
- Точный механизм генерации `nonce` (инкрементальный счётчик на контракте vs.
  случайное число на клиенте) — решается в implementation-плане.
- Выбор между `personal_sign` и `eth_signTypedData_v4` (EIP-712) для подписи
  — решается в implementation-плане; предпочтителен EIP-712 как более
  безопасный и читаемый в MetaMask.
